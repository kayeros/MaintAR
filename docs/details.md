# MaintAR — подробности

Полное описание возможностей, API бэкенда и устройства проекта (раньше было в README).

## Что умеет

- **Вход.** Регистрация с подтверждением почты кодом. Для показа есть демо-доступ: логин `demo`, пароль `demo12345`. Есть восстановление пароля по коду из письма. Логин без «@» дополняется до `@maintar.local`.
- **Поиск оборудования** по QR-коду (камера) или по коду/серийному номеру с шильдика. QR со ссылкой (`http://VALVE-001`, `...?code=VALVE-001`) тоже распознаётся. Если не получилось, есть ручной выбор из списка. Найденное оборудование запоминается в «Недавно найденных».
- **Карточка оборудования:**
  - статус по последнему осмотру;
  - блок «Сначала проверьте» с причинами словами: узлы с дефектом или «рекомендуется проверка» на последнем осмотре, с выработанным ресурсом или остатком меньше 15 %, без данных о ресурсе. Кнопка «Сфотографировать узел» открывает камеру с подсказкой «Наведите камеру на: <узел>»;
  - фото оборудования (снять или выбрать из галереи), паспорт;
  - узлы и ресурс;
  - история осмотров всех инженеров (фото, статус, дата, кто проводил);
  - журнал работ;
  - список дефектов, которые проверяет ИИ.
- **Осмотр по фото.** Фото отправляется на бэкенд, тот вызывает сервис ИИ. Результат приходит с рамками дефектов на снимке, категорией («Возможный дефект», «Рекомендуется проверка», «Видимых проблем не обнаружено»), уверенностью, пояснением и рекомендацией. Нажатие на рамку или находку открывает экран узла. Фото осмотра сохраняется на сервере и видно в истории.
- **Экран узла:**
  - нормативный срок;
  - расчётный остаток (от даты замены или установки);
  - фактическое состояние по фото с последнего осмотра;
  - журнал работ по узлу и кнопка «Записать работу».
  Если дат нет, выводится «Недостаточно данных для оценки ресурса».
- **Журнал работ.** Записи «Проверил», «Обслужил», «Заменил» или «Заметка» с комментарием и датой. После «Заменил» ресурс узла считается заново.
- **История:** свои осмотры и свои работы (запись можно удалить).

## Запуск связки

Три части на одном ПК, телефон с Expo Go в той же сети Wi-Fi. Всё сразу поднимает `start-all.bat`.

| Часть | Где | Порт | Запуск |
|---|---|---|---|
| Сервис ИИ (YOLOv8) | `ai_service/` | 8000 | `ai_service\run.bat` |
| Бэкенд MaintARBackend (.NET 11) | `backend\MaintARBackend` | 5176 | `dotnet run --launch-profile http --urls http://0.0.0.0:5176` (Development) |
| Приложение (Expo) | этот репозиторий | 8081 | `npm install`, затем `npx expo start --lan --clear` |

1. Бэкенд лежит в этом репозитории, в папке `backend` (перенесён из репозитория MaintARBackend). Локально работает на SQLite. Скопируйте `backend\MaintARBackend\appsettings.Local.example.json` в `appsettings.Local.json` (он не в git) и задайте `Database:Provider=Sqlite`, ключ JWT, токен Resend и адрес сервиса ИИ. База и демо-оборудование создаются при первом запуске. В режиме Development код подтверждения почты дублируется в консоль бэкенда.
2. Адрес бэкенда для приложения задаётся в `.env`: `EXPO_PUBLIC_API_URL=http://<IP компьютера>:5176` (образец в `.env.example`). Его можно поменять в «Профиле».
3. В терминале Expo появится QR-код: на Android его сканируют из Expo Go, на iPhone штатной камерой. Проверка без телефона: откройте `http://localhost:8081` в браузере (камера там недоступна, фото выбирается из галереи).
4. Если телефон не видит сервер, откройте порты в брандмауэре:
   `netsh advfirewall firewall add rule name="MaintAR" dir=in action=allow protocol=TCP localport=8081,5176,8000 profile=private,public`

Демо-оборудование: `VALVE-001` (задвижка), `TRANS-001` (трансформатор), `MOTOR-001` (электродвигатель).

## Сценарий показа

1. Войти: логин demo, пароль demo12345.
2. Ввести `MOTOR-001` или отсканировать QR → карточка → «Сначала проверьте».
3. «Сфотографировать узел» → результат с рамками.
4. Нажать на рамку → экран узла с ресурсом.
5. «Записать работу».
6. Вернуться в карточку → «Осмотры» и «Журнал работ».

## API бэкенда, которое использует приложение

| Метод | Назначение |
|---|---|
| `POST api/Auth/login`, `register`, `send-verification-code`, `verify-email` | вход и подтверждение почты |
| `GET api/Equipment/identify?value=` | поиск по коду или серийному номеру |
| `GET api/Equipment`, `GET api/Equipment/{id}` | список для ручного выбора, карточка |
| `POST api/Equipment/{id}/photo` | фото оборудования |
| `POST api/Inspections` | осмотр: фото + код, анализ ИИ |
| `GET api/Inspections/my`, `GET api/Inspections/{id}` | свои осмотры |
| `GET api/Inspections/equipment/{id}`, `.../equipment/{id}/{inspectionId}` | все осмотры оборудования |
| `api/Maintenance` (POST, GET equipment/component/my, DELETE) | журнал работ |

## Где что лежит

| Файл | Содержимое |
|---|---|
| `App.js` | экраны и навигация |
| `src/api.js` | клиент бэкенда: токен, ошибки на русском, загрузка фото, нормализация QR |
| `src/theme.js` | цвета |
| `ai_service/app.py` | сервис ИИ: `POST /analyze` → находки с рамками в формате бэкенда |
| `start-all.bat` | запуск всех трёх частей |
| `backend/` | бэкенд MaintARBackend (ASP.NET Core): учётные записи, оборудование, осмотры, журнал работ |
| `server/`, `src/engine.js`, `src/data/`, `src/AuthScreen.js`, `src/auth.js` | ранний прототип (офлайн-правила и датчики кейса), приложение их больше не использует |

## Ограничения

- Анализ по фото предварительный. Отсутствие видимых дефектов не подтверждает исправность. Решение принимает инженер.
- Модель находит только 5 классов дефектов и не проверяет, есть ли на фото оборудование: случайный снимок даст «Видимых проблем не обнаружено». Базовая модель (коррозия, трещины) обучена полностью, mAP50 0,77. Расширенная (утечка, изоляция кабеля, крепёж) прошла 2 эпохи из 30, эти классы находятся плохо.
- Рамки рисуются поверх снимка, а не поверх живого видео.
- Расчётный остаток считается по календарю от даты замены или установки, без учёта наработки и датчиков.
- «Фактическое состояние по фото» берётся из последнего осмотра оборудования. Если на нём узел не попал в кадр, будет «видимых проблем не обнаружено».
- Журнал работ (`MaintenanceController`) в `backend` — временная реализация по контракту, который согласовали с автором бэкенда. Основной контроллер он делает сам.
- Сервер и телефон должны быть в одной сети. Облачного развёртывания нет.
